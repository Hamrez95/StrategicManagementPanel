# پشتیبان‌گیری و تمرین بازیابی

این روش برای استقرار فعلی Docker Compose با PostgreSQL و فایل‌های خصوصی در `/private-files` است. دسترسی به کنسول خصوصی و یک مقصد محلی امن لازم است. بکاپ شامل اطلاعات کاربران است؛ آن را داخل Git، وب‌سرور، پوشهٔ عمومی، تیکت یا خروجی ابزارها نگذار. مقصد نهایی باید رمزگذاری و دسترسی محدود داشته باشد.

## گرفتن snapshot هماهنگ

برای هماهنگی دیتابیس و فایل، یک بازهٔ توقف نوشتن تعیین کن. اسکریپت API همین پروژه را موقتاً متوقف می‌کند و سپس دوباره بالا می‌آورد؛ هر نویسندهٔ بیرونی، worker یا job مستقل را هم قبلش متوقف کن. توقف فقط API کافی نیست اگر سرویس دیگری به همان دیتابیس یا فایل‌ها می‌نویسد. ابتدا در محیط آزمایشی اجرا کن.

از ریشهٔ ریپو، با PowerShell و نام دقیق کانتینرهای همان پروژه:

```powershell
./scripts/backup-recovery.ps1 `
  -DbContainer '<project>-db-1' `
  -ApiContainer '<project>-api-1' `
  -OutputDirectory '.local-backups/<new-snapshot-id>' `
  -StopApiForSnapshot `
  -TestRestore
```

نام دیتابیس و کاربر PostgreSQL پیش‌فرض `stratino` است؛ در صورت تفاوت، `-Database` و `-DbUser` را مشخص کن. گذرواژه را در فرمان ننویس؛ ابزار از دسترسی داخلی PostgreSQL کانتینر استفاده می‌کند. اگر تنظیم احراز هویت محیط این روش را نمی‌پذیرد، آن را با کنسول خصوصی تنظیم کن؛ احراز هویت را برای بکاپ ضعیف نکن.

خروجی باید یک پوشهٔ تازه باشد؛ فایل قبلی بازنویسی نمی‌شود. دسترسی پوشهٔ تازه در Windows به حساب اجراکننده و SYSTEM محدود می‌شود؛ در Linux پوشه با مجوز 0700 نگه داشته می‌شود. این کنترل جای رمزگذاری یا حفاظت مقصد مستقل را نمی‌گیرد. کانتینرها باید برچسب یک پروژهٔ Compose داشته باشند. بعد از توقف هماهنگ نوشتن، `pg_dump` و کپی فایل‌ها گرفته می‌شوند. API در مسیر خطا هم دوباره راه‌اندازی می‌شود و سلامت آن بررسی می‌شود. `receipt.json` شامل هش دو آرشیو، تعداد/حجم فایل، زمان‌ها و نتیجهٔ دقیق restore است؛ محتوای فایل، نام فایل خصوصی یا credential در خروجی کنسول چاپ نمی‌شود.

گزینهٔ `-TestRestore` یک دیتابیس با نام تصادفی و مستقل می‌سازد؛ dump را بازیابی می‌کند، شمارش و digest شناسه‌های کلیدی را تطبیق می‌دهد، migration و audit یکپارچگی را اجرا می‌کند و سپس همان دیتابیس موقت را حذف می‌کند. فایل‌ها در `restored-files` داخل پوشهٔ خصوصی snapshot بازیابی می‌شوند؛ فایل‌های زنده جایگزین نمی‌شوند. ابزار پوشهٔ snapshot یا خروجی بازیابی را خودکار حذف نمی‌کند؛ آن‌ها هنوز دادهٔ خصوصی‌اند.

موفقیت فرمان به‌تنهایی کافی نیست: `restore_verified`، تعداد فایل و نبود guard مفقود را در receipt بررسی کن. اگر تعداد فایل صفر باشد، فقط بازیابی مجموعهٔ خالی اثبات شده؛ آن را آزمون فایل مشتری معرفی نکن. هر اجرای ناموفق یا مقصد ناقص را ناموفق نگه دار؛ از آن برای عرضه استفاده نکن.

## تضمین‌های آرشیو فایل

ابزار `apps/api/scripts/private_file_snapshot.py` فقط فایل‌های معمولی را ثبت می‌کند. manifest داخلی برای هر فایل مسیر نسبی، اندازه و SHA-256 دارد. فایل صفر‌بایتی و نام فارسی حفظ می‌شوند. ایجاد snapshot به اعلام صریح توقف نویسنده‌ها نیاز دارد. تغییر فایل در هنگام خواندن رد می‌شود؛ این کنترل جای توقف هماهنگ همهٔ نویسنده‌ها را نمی‌گیرد.

بازیابی تنها در یک پوشهٔ تازه انجام می‌شود. مسیر مطلق، `..`، مسیر Windows با درایو، لینک نمادین/سخت، sparse file، عضو تکراری، manifest نامعتبر، فایل اضافه/گم‌شده و checksum نادرست پذیرفته نمی‌شوند. بعد از بازیابی، مجموعهٔ فایل‌ها و هش‌ها دوباره بررسی می‌شوند. پوشهٔ ناقص در خطا حذف خودکار نمی‌شود؛ منبع حفظ می‌شود و بررسی خصوصی لازم است. آرشیو را از ورودی مشتری یا منبع نامطمئن نپذیر.

SHA-256 سلامت بایت‌ها را بررسی می‌کند؛ امضای اصالت یا رمزگذاری نیست. receipt و کلیدهای لازم را با کنترل دسترسی جدا نگه دار. انتخاب مقصد مستقل، رمزگذاری، نگهداری نسخه‌ها و حفاظت از حذف باید در محیط مقصد تنظیم و آزموده شود؛ این اسکریپت خودکار فایل را به حساب ابری یا شخص دیگری ارسال نمی‌کند.

## بازیابی پس از حادثه

۱. ترافیک نوشتن را ببند و از وضعیت حادثه snapshot مستقل بگیر. آخرین زمان نوشتن را ثبت کن تا دادهٔ پس از بکاپ بی‌صدا حذف نشود.
۲. dump و فایل‌ها را همراه receipt از مقصد مستقل بیاور و هش آرشیوها را پیش از بازکردن مقایسه کن.
۳. بازیابی را ابتدا روی دیتابیس، فایل و برنامهٔ جدا اجرا کن. migrationها باید با نسخهٔ کد مقصد سازگار باشند. صرفاً برای برگرداندن کد، تاریخچهٔ ممیزی را حذف نکن.
۴. نسخهٔ امن تنظیمات و کلیدهای لازم را از مخزن رازهای مستقل برگردان. کلید رمزگذاری MFA، کلیدهای سرویس‌های بیرونی و سیاست تعویض کلیدها جزو dump دیتابیس یا آرشیو فایل نیستند. credential را در receipt نگذار.
۵. قبل از استفادهٔ سرویس از فایل‌های بازیابی‌شده، مالکیت و مجوز آن‌ها را با UID حساب اجرای سرویس مقصد هماهنگ کن. صحت بایت‌ها به معنی دسترسی درست سرویس به فایل‌ها نیست. علاوه بر audit مدل‌ها، ورود و MFA، جداسازی فضاها، دانلود فایل خصوصی، پیشرفت درس و وضعیت سفارش/اشتراک را در محیط مقصد بررسی کن. فقط با موفقیت این جریان‌ها و تصمیم مالک، ترافیک را منتقل کن.

## شواهد و باقی‌مانده‌ها

- ۲۰۲۶-۱۰-۲۶: بازیابی واقعی dump محلی در دیتابیس جدا، تطبیق شناسه‌ها/شمارش، migration و audit با ۷۷ مدل، ۱۸۰ بررسی، صفر تخلف و بدون guard مفقود موفق بود.
- ابزار هماهنگ روی کانتینرهای محلی اجرا شد؛ snapshot و restore دیتابیس و restart سلامت API موفق بود. حجم فایل خصوصی واقعی در این محیط صفر بود؛ هیچ فایل ساختگی به فضای کار کاربر اضافه نشد.
- آزمون‌های منفی و round-trip مستقل با دو فایل مصنوعی، ۷۶۸۰۰ بایت، نام فارسی و فایل صفر‌بایتی پوشش دارند؛ این شاهد را از آزمون دادهٔ واقعی محیط مقصد جدا نگه دار.
- شکست عمدی snapshot روی یک کانتینر آزمایشی جدا بررسی شد؛ سرویس آزمایشی دوباره اجرا و سالم شد. API کاربر برای تزریق خطا متوقف نشد. CI نیز بازیابی دیتابیس و فایل مصنوعی غیرخالی را بررسی می‌کند؛ موفقیت CI هر head باید جدا تأیید شود.
- مقصد مستقل خارج میزبان، رمزگذاری و بازیابی کلیدها، زمان‌بندی/هشدار، سیاست نگهداری و RPO/RTO مصوب هنوز تنظیم نشده‌اند. برای آن‌ها نتیجه یا زمان تضمین‌شده اعلام نکن. تسک #31 تا تحقق همین معیارها باز می‌ماند.
