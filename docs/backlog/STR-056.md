# STR-056 — مالکیت canonical داده و مهاجرت تدریجی پروفایل

Priority: **P0** | Epic: **MOS-TWIN** | Status: in_progress; packets A/B/C complete locally, final database/restore and acceptance gates pending. Dependencies: STR-005, STR-018, STR-021.

## Context / Problem

Profile JSON stores products/segments/ICPs/goals while execution.Goal separately owns goals; duplicate inputs threaten Business Twin consistency.

## Goal / User value

Define canonical ownership/bindings for profile, segments, ICP, product/service and existing execution.Goal; no new duplicate Business entity. The manager reuses trustworthy business information and reaches a defensible next action with less repeated input.

## Scope / Functional requirements

- Define canonical ownership/bindings for profile, segments, ICP, product/service and existing execution.Goal; no new duplicate Business entity.
- Implement additive scoped records and dry-run importer with stable old-ID mapping, conflict report, backup and idempotent apply.
- Keep compatibility projections for profile/import/report consumers; one write owner with revision and auditable rollback.

## Non-goals

No new hosting, paid services, generic workflow DSL, graph database, arbitrary health score or opaque AI decision logic. Preserve legacy tools; no unrelated domain expansion. No decorative UI or invented production endpoint is required.

## Domain impact / Data requirements

Follow the ownership and contracts in [ARCHITECTURE](../management-os/ARCHITECTURE.md). Workspace ID and explicit venture/segment/period context, revision, canonical references and provenance are required. No second ICP/revenue/Goal copy. Additive migrations, stable old-ID map, dry-run, source backup, idempotent apply and rollback parity are required.

## Knowledge-base dependencies

- `assets/management-knowledge/evidence/evidence-model.md`
- `assets/management-knowledge/taxonomy/business-types.json`

## UX requirements / Accessibility

Return actionable bounded errors with affected IDs/fields; do not leak evidence or require managers to understand engine internals. When surfaced in UI, unknown/invalid/stale states need text and keyboard-accessible explanation, not color alone.

## AI involvement / Deterministic logic

AI has no authority in this task. Reviewed IDs, versions, permissions, derivation, formulas, gates and completion are deterministic; source prose is never eval-executed. Any later AI wording is a reviewable draft outside this scope.

## Security / Privacy

Enforce server-side membership and same-Workspace nested references on all reads/writes/import/export/jobs. Viewer cannot write; revoked membership loses access. Use redacted logs, minimal personal data and revision/idempotency protections.

## Acceptance criteria

- [ ] Given an ICP already saved in profile, journey and customer view reference the same migrated identity and ask no duplicate input.
- [ ] Given two goal records with uncertain equivalence, dry-run reports a conflict instead of merging by title.
- [ ] Given migration run twice or rolled back to compatibility reads, no entity/history is lost and cross-Workspace IDs are rejected.

## STR-056-A — additive context and customer schema

Status: complete locally; schema migration and importer dry-run/apply remain pending.

Added `modules.customer_context` with Workspace-scoped Product, Segment and IdealCustomerProfile models, revision constraints, an explicit half-open-period `ContextRef`, and a typed old-ID map with actual foreign keys. `legacy_canonical_id` derives UUIDv5 from Workspace, source namespace, entity type and exact legacy ID; repeated imports therefore receive the same canonical ID, while different workspaces/sources/types remain isolated. Map validation rejects a target from another Workspace. Existing profile JSON is unchanged and remains the sole profile write owner; existing `execution.Goal` stays canonical and no goal copy or title-based merge was added. ICP nested segment, evidence and assumption data remain marked frozen compatibility snapshots until their typed bindings exist.

Validation: the focused no-database Django suite passed 6/6 at the packet-A checkpoint; Django system checks report no issues; migration autodetection finds no model/migration drift; `git diff --check` passes. PostgreSQL migration/restore and server, Docker, physical/browser checks remain queued for final acceptance. No canonical records have been applied and no customer-facing endpoint/write path is active.

## STR-056-B — dry-run migration plan and compatibility projection

Status: complete locally; reviewed idempotent apply and write-owner cutover remain in packet C.

`build_profile_import_plan` hashes and preserves the untouched profile snapshot, produces stable typed mappings for valid Product/Segment/ICP rows, records original collection positions, and bounds diagnostics to 256 while reporting suppressed count. Duplicate IDs and noncanonical IDs are not normalized into new identities. Unmappable nested ICP segment data is retained with a review conflict. Profile goals stay deferred; same-Workspace execution Goals with matching normalized titles are flagged as candidates, never merged. Mission/problem narrative stays under WorkspaceProfile ownership. `project_legacy_profile` reconstructs the existing JSON response shape and item order from canonical records only when every target has an explicit identity mapping and same-Workspace binding. No records were applied and no read/write path was switched.

Validation: all 16 focused no-database Django tests pass, including duplicate/foreign IDs, exact source backup/order, bounded conflict reporting, Goal title ambiguity, ICP snapshot preservation and projection round-trip. Ruff E/F/I checks pass; system checks report no issues; offline migration autodetection reports no drift. PostgreSQL/restore and other server, Docker, physical/browser checks remain deferred. Issue #68 remains open pending packet C and final acceptance.

## STR-056-C — reviewed apply and canonical write owner

Status: complete locally; PostgreSQL upgrade/restore, full acceptance, remote merge and issue closure remain pending.

`apply_profile_import` applies one reviewed cutover per Workspace inside a transaction. It locks the Workspace/profile, requires owner permission, checks the reviewed revision and source digest, validates explicit conflict acknowledgements, creates canonical rows and typed FK identity maps, preserves the full source snapshot and plan, updates profile revision/history, and returns the same batch for an exact idempotent retry. Goal records remain owned by `execution.Goal`; no title-based merge occurs. The existing `update_workspace_profile` service remains the write boundary after cutover: canonical rows and the current legacy-shaped response projection update in the same transaction. Stable old IDs and collection order remain mapped; identity changes and deleting a referenced Segment fail with actionable conflicts.

Validation: focused `modules.customer_context` suite passes 20/20 on a temporary in-memory SQLite database, including migration application, owner/viewer permissions, exact backup, idempotent retry, digest-mismatch rollback, and post-cutover canonical/compatibility writes. Django system check passes; Ruff E/F/I passes for new/changed code (legacy E501 findings in the pre-existing profile service are excluded). Offline migration autodetection reports no drift for the changed `customer_context` and `workspaces` apps; unrelated framework/version drift appears in `auth`, `accounts`, `contenttypes` and `sessions`. Graphify updated to 4,331 nodes / 8,379 edges / 263 communities; changed consumers include `update_workspace_profile`, profile history and compatibility projection. SQLite is local logic evidence only; PostgreSQL migration/restore, server, Docker, physical/browser acceptance remain in the final queue. No rows from real profiles were migrated. Issue #68 remains open.
